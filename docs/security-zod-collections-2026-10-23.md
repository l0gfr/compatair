# Zod collection resource bounds, 23 October 2026

GitHub advisory [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) blocks the publication with Zod 4.4.3 and the legacy Zod 3.25.76 used by Chromium BiDi in Lighthouse. The release severity policy remains unchanged, including for development dependencies.

Astro and sitemap retain the official Zod 4.6.7 release. The browser-facing direct dependency uses Zod 4.4.3 with a separate, byte-attested backport of the official collection bound correction. The 4.6.7 upgrade added approximately 7,100 gzip bytes to each affected browser journey and failed ten existing budgets. A client-only comparison isolates this change without rebuilding the 49,052 static pages. The backport carries the early Array/Map/Set size checks, their helper and declarations, without the unrelated memoizer, schema construction or JSON Schema changes. Its exported v3 subtree also receives the already reviewed early Array/Set rejection. The 24-hour quarantine and upstream archive integrity checks remain mandatory; unrelated transitive versions are preserved.

Chromium BiDi 14 uses Zod 3 APIs. Replacing that package with Zod 4 breaks its schemas. A small local backport therefore retains the existing array and set size errors but stops before traversing oversized constrained collections. It covers array maximum/exact length and set maximum/exact size, synchronous and asynchronous parsing, in the ESM and CommonJS runtime files and the accompanying TypeScript source. Valid boundary inputs, custom messages and nested paths are preserved.

This changes the handling of already-invalid oversized input: element preprocessors and refinements no longer execute after the collection exceeds its declared upper bound. It does not invent a bound for unconstrained schemas. The old package also bundles an experimental v4 subtree. Its shared core receives the same early upper-bound checks for arrays, maps and sets in ESM, CommonJS and the accompanying source. A private payload marker prevents the same size error from being emitted again by the older outer check loop. Prefix-only size checks follow the upstream rule: a preceding custom check may rewrite the value, so it prevents the shortcut. Public custom when callbacks also disable the shortcut, preserving their single evaluation on the post-parse value. Legacy v3 records the outcome of its existing size check instead of reading a collection size again, including for Set subclasses with stateful accessors. The verified BiDi consumer resolves the patched v3 entry; the direct application consumer uses the separately attested 4.4.3 backport, while Astro and sitemap retain the official corrected 4.6.7 version.

The dependency audit separately and mandatorily attests both exact patch files, workspace declarations, lock hashes, all installed 3.25.76 and 4.4.3 copies, CJS/ESM entry bridges and v3/v4 implementations. It also verifies the official 4.6.7 copies and the direct, Astro, sitemap and Lighthouse/Puppeteer/Chromium-BiDi resolutions. The attestation token binds both patches; the old legacy-only token cannot waive the advisory. A mismatched, missing or extra vulnerable copy fails publication. The known advisory remains reported as locally corrected only after this attestation passes. The GitHub client preserves the advisory identifier, vulnerable version ranges, first patched versions and exact queried locked versions. Recognition requires the reviewed range < 4.6.6 and first fix 4.6.6: an extension affecting 4.6.7, a changed range, missing range metadata, changed title, URL, package or severity, another advisory, or missing attestation remains blocking. Existing cache/Lighthouse patch attestations remain mandatory.

Regression tests cover upper bounds, absence of per-element work on oversized input, both module systems, asynchronous parsing, nested error paths, tampered bytes/configuration/resolutions and unrelated security advisories. A real clean frozen installation, installed-copy attestations and 75 focused tests passed in the isolated repair probe. The direct backport is additionally checked against the installed official 4.6.7 implementation for limits, coercion, conditional checks, prefix rewrites, Set/Map transformations, parse direction and exact diagnostics. Its early bound semantics intentionally follow the official correction rather than every behavior of the old uncorrected version. The repository tests and publication gates must still pass on the final candidate before deployment.

The direct backport guards one upstream edge case: a stateful Set size getter can stop the bound check from emitting an issue. It marks early abort only when an issue was actually appended, avoiding the upstream 4.6.7 TypeError without removing a size constraint. Both module systems have a dedicated regression test.

The final advisory check also detected [GHSA-xjj6-f33q-929c](https://github.com/advisories/GHSA-xjj6-f33q-929c) in the locked Undici 8.10.2 used by unifont. The lock now selects the official 8.12.2 correction within unifont’s existing ^8.0.0 range, without a major upgrade or an advisory exception. Its registry signature, archive SHA-512 and publication age were verified before the frozen installation.

## Dependabot verification, 24 October 2026

The frozen installation and 144 focused tests passed on Node 24.21.0, including installed Zod bounds, tampered-patch rejection, advisory classification, fast-uri, body-parser, Undici and application consumers. Source lint and the dependency audit also passed without a full site build. The fast-uri override and lock now use the official 3.1.9 correction for alerts 20 through 23.

Dependabot alerts 18 and 19 identify the unmodified Zod version numbers in the manifest and lock. The corresponding installed implementations are locally remediated by the verified backports described above, not official patched-version upgrades. These alerts can be classified as inaccurate for the verified patched tree with this document as evidence. This classification is limited to GHSA-mrhx-c7xc-m3w5 and its constrained-collection issue. The mandatory byte attestations, behavioral tests and fail-closed advisory policy remain in place; any changed patch, vulnerable resolution or advisory still requires review.
